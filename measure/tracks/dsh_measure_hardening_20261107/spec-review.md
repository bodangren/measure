# Spec Review: dsh_measure_hardening_20261107

Author model: deepseek-official/deepseek-flash

## Round 1

Date: 2026-11-07
Reviewer: subagent (fresh context, default model)

### What this track proposes
The track hardens the DSH Measure adapter on three fronts. S1 replaces the live check's module-path identity with a SHA-256 digest over a fixed code file list, computed once when the plugin module is evaluated and served as `x-measure-guard-digest`; `bin/measure-dsh --check --live` compares it with a digest of the source folder (absent → WARN, mismatch → FAIL, equal → PASS), while `install` writes the profile patch even when unchanged and a new `reload` action performs that write on demand so a running Host recomposes. S2 adds git-backed verification at turn end (each `[x]` task's SHA must exist and carry a git note) and denies a `measure/tracks.md` close whose track `metadata.json` `actual_tasks` disagrees with the plan. S3 closes write-path bypasses (registry/plan writes through `apply_patch` and `str_replace_editor` are denied, shell `>`/`>>`/`tee`/`sed -i` targets are path-checked, an in-command `git add` joins the commit guard's set) and S4 covers docs, live evidence, and closeout.

### How the current system works, per this spec
The plugin's state route identifies the loaded Host module by file URL (`x-measure-guard-module`, `src/client-state.js:100`), so `--check --live` compares a path and keeps passing after the installed files are replaced under a running Host. The guards are marker-based: the end-of-turn check reports only `[x]` tasks with no SHA, the closeout denies only a track whose plan has an open task, `closeoutGuardFor` allows every mutation that has no after-text (`src/guard.js:111`), and a bash call is an opaque shell command checked only by the strict commit guard. The commit guard takes `git diff --cached` plus, when the command has `-a` or an earlier `git add`, all changed and untracked status paths (`src/commit.js:18-23`, `src/core/guards.ts:350`), and `install` with an unchanged managed block writes nothing. The verification layers are `node --test` over `plugins/dsh-measure-guard/tests/*.test.js` (213 tests at HEAD), `tests/dsh/run.sh`, both parity gates, and `tests/spec_review_gate/run.sh`.

### Findings
- F1 [Blocker] spec.md Decision 3 and Story S4: the live item compares the loaded digest with the digest of the source folder, but Story S4 proves staleness by replacing the installed `src/status.js` without recompose; the loaded digest is the digest of the old installed bytes and the source is untouched, so the live item still PASSes, and after `reload` the Host loads the modified installed bytes, which no longer equal the source, so the item FAILs again. Rationale: the track's own acceptance evidence cannot be produced and an out-of-band replacement of the installed copy — the failure mode the track exists to catch — stays undetected; the spec never decides whether the reference is the source folder or the installed copy.
- F2 [Blocker] plan.md Task 1.1: the digest byte stream is unspecified — `computeDigest(packageDir)` must produce `sha256:<hex>` from a Node read while the bash `source_digest()` hashes the same list, yet the plan names neither the framing (relative names, separators, per-file digests versus concatenated bytes) nor the enumeration rules, and `src/**/*.js` selects different sets under a bash `find` and a Node directory walk. Rationale: S1's whole claim is that two independent implementations agree, so an implementation choice here silently makes every live check PASS or FAIL, and no test pins the shared format.
- F3 [Blocker] plan.md Task 2.1: the proposed seam `gitOk(args, cwd)` is a non-throwing boolean meaning "exit 0", but `git cat-file -e` exits 1 for a missing object and 128 for a fatal error, and `git notes show` exits 1 for a missing note, so the boolean cannot distinguish "no commit or note" (Decision 5: a problem) from "git cannot answer" (Decision 5: fail open). Rationale: the seam's API shape cannot express the required edge-case behavior, so the implementer must invent a discriminator (a probe command, stderr parsing, or exit-code classes) that the plan does not choose.
- F4 [Blocker] plan.md Task 2.2 and Task 3.2: test placement is left open — "`tests/end-of-turn.test.js` or `tests/closeout.test.js`" (line 39) and "`tests/edit-guard.test.js` / `tests/commit.test.js` / `tests/closeout.test.js`" (line 54) — so the plan never says which existing file receives each new case. Rationale: file location is a design choice the plan must make, and the alternative forms leave the Red cases without a concrete home.
- F5 [Major] spec.md Decision 9 and plan.md Task 3.1 (`addedPaths`): the Overview and Decision 9 state that a `git add` inside the same commit command is invisible to the commit guard's no-task rule, but `parseCommitCommand` already sets `takesChanges` when an earlier `git add` is present (`src/core/guards.ts:350`) and `stagedFiles` then unions every changed and untracked status path (`src/commit.js:18-23`), so `git add src/app.js && git commit …` already denies and already lists `src/app.js` (README.md:151). Rationale: the new parser duplicates existing behavior, the named Red test would already pass, and the residual gap the change actually closes (`git add -f` on an ignored path, or pathspec-only adds) is not what the acceptance criterion specifies.
- F6 [Major] spec.md Decision 8 and Story S3: the shell check ignores every target inside `measure/`, so a redirect, `tee`, or `sed -i` that rewrites `measure/tracks.md` or a plan still bypasses the closeout guard and the new `actual_tasks` check, while Decision 7 denies those same files through `apply_patch`/`str_replace_editor`. Rationale: this leaves the highest-stakes registry write unseen by the story that closes write-path bypasses, and the end-of-turn backstop does not verify `metadata.json`, so the new enforcement can be routed around.
- F7 [Major] spec.md Story S1 and plan.md Task 1.1 (`reload`): the plan adds a `reload` action but specifies no CLI shape for it — which of `--dsh-home`/`--profile`/`--dry-run` it accepts, its exit codes (the CLI's documented 0/1/2/3), its output, or what it does when the profile or patch file is missing (the spec only says "reports success"). Rationale: exit codes and flags are the CLI contract that `tests/dsh/test-reload.sh` and the live sequence must assert, and an undefined contract cannot be tested or documented.
- F8 [Major] plan.md Task 1.2: the named digest tests cover determinism, order independence, a changed file, the exclusion list, and the route header, but none covers the design's two properties — that the bash `source_digest` and the JS `computeDigest` produce the same value for the real package, and that the header keeps the load-time digest after a file changes. Rationale: without those checks a divergent file list, framing, or line-ending rule ships green, and the "computed exactly once at module evaluation" criterion has no test.
- F9 [Major] plan.md Task 1.2 (`tests/dsh/test-check.sh`): the three live-item cases (mismatch, absent header, match) need an HTTP endpoint that answers with a chosen header, but the test world unsets `DSH_WEB_URL` (`tests/dsh/lib.sh:130`), `live_check` calls `curl` against it, and the plan names no stub server, stub `curl`, or `lib.sh` change. Rationale: the named live cases cannot run in the existing harness without a fixture the plan leaves to the implementer.
- F10 [Major] plan.md Task 1.1, Task 2.1, Task 3.1: each "Contract" task as written creates production code (`src/digest.js` with `computeDigest`, the `index.js` load-time capture, the route header, the CLI comparison, `src/git-verification.js`, `src/shell.js`), while the phase header says "contract first, a failing test recorded in the git note, then the implementation" (lines 6-8) and NFR-7 requires Red-first tests; Task 1.3 then implements the same items again. Rationale: the plan does not say what a "Contract" task delivers (signatures/stubs or working code), so the Red phase can be skipped or the two tasks collide.

## Round 2

Date: 2026-11-07
Reviewer: subagent (fresh context, default model; the required re-review)

### What this track proposes

The track makes the DSH Measure adapter prove three claims. First, a SHA-256 digest over a fixed manifest of the plugin package is captured when the module is evaluated and served as `x-measure-guard-digest`, `bin/measure-dsh --check --live` compares it with the digest of the installed copy, and `install`/a new `reload` action write the profile patch as the recompose trigger. Second, the end-of-turn check verifies each `[x]` task's SHA with a tri-state git probe and the closeout guard checks a closed track's `metadata.json` `actual_tasks` against its `[x]` count. Third, three write-path gaps close: `apply_patch`/`str_replace_editor` are denied on the registry and track plans, shell redirection/`tee`/`sed -i` targets are path-checked (with a registry deny), and an in-command `git add` contributes a narrowed file set instead of every status path. S4 documents the changes and records a live stale-instance demonstration plus the track closeout.

### How the current system works, per this spec

`plugins/dsh-measure-guard/` is a plain-ESM DSH Host plugin (plus a hand-written client half) whose guard decisions read a per-root cached snapshot of `measure/` through an `io` seam (`makeIo` in `src/snapshot.js`), whose git calls collapse every failure to an empty result. `bin/measure-dsh` copies the plugin into the profile under a stamp that protects local edits, writes one marker-managed `cordis.patch.yml` row, and its `--check --live` only compares the route's `x-measure-guard-module` path with the installed `index.js`, so replacing the installed bytes leaves the check passing while the Host runs stale code. The closeout guard reads only `edit`/`write` after-texts, so `apply_patch`, `str_replace_editor`, and shell writes reach the registry and plans unchecked, and a `git add` earlier in the same command sets `takesChanges` and makes the commit guard treat every changed and untracked status path as staged. The end-of-turn check reports marker-only problems from `turnProblems` and never probes the commits or their notes.

### Findings

- F8 [Major] plan 1.2 (digest tests): the tests still do not cover the load-time capture that S1 requires ("computed exactly once and the digest is served unchanged for the instance's lifetime"); `tests/digest.test.js` names determinism, creation-order independence, a changed covered file (which re-computes), and the file list, and `tests/client-state.test.js` only asserts that an injected `deps.digest` is echoed. Rationale: the bash-vs-Node half is now tested, but no named test fails if `index.js` recomputes the digest per request instead of capturing it once at module evaluation.
- F11 [Major] plan 2.1/2.2 and spec Decision 6: one deny text with `<n>`/`<m>` covers every metadata failure, but the missing/malformed `metadata.json` case (a deny in Decision 6) has no `actual_tasks` value and 2.2 asks the "missing" case to deny "with both numbers"; `closeoutMetadataCheck(deps, closing)` also has no argument from which to build `<tracks dir>/<folder>/metadata.json`, because `closing` entries carry only a relative folder. Rationale: the implementer must invent the missing/malformed texts and add a parameter (the committed `src/guard.js` already passes a third `path` argument), and the named test asserts a contradiction.
- F12 [Major] spec Decision 9 and plan 3.1: the narrowed `git add` grammar contributes non-option path arguments, a `.`/pathspec-only form, and `git commit -a/--all`, but `git add -A/--all` and `git add -u/--update` are options with no path token, so they contribute nothing and `git add -A && git commit -m "feat(x): y"` with no `[~]` task now passes the commit guard that denied it before; "an unresolvable pathspec sets `all`" is also undefined for a function that receives no root. Rationale: the fix for the over-broad union opens a new bypass in the guard area the track exists to harden.
- F13 [Major] spec Decisions 5-7 and plan 2.1/2.2/3.1: none of the new checks (git problems, metadata closeout, unreadable-tool deny, shell registry deny) states how it behaves in `advise` mode or with the `/measure-off` bypass, while README "Modes" says `advise` allows every guard; the wired `closeoutMetadataCheck` call in `src/guard.js` runs after `trackCloseDecision`'s `isGuarding` gate but unconditionally, so an `advise` session can now have a track close denied. Rationale: the mode/bypass condition is a real edge-case choice, and the committed code already contradicts the documented mode contract.
- F14 [Major] spec S4 and plan 4.2: the live sequence replaces the installed `src/status.js`, ends at `--check --live` PASS with the modified bytes installed, and never restores the file; `copy_plugin` in `bin/measure-dsh` keeps a local edit and re-stamps the previous hash, so later `install` runs preserve the tampered file. Rationale: the evidence step leaves the live profile's installed plugin permanently divergent from the source, with `--check` reporting "edited src/status.js" from then on, and the plan neither documents nor repairs that state.
- F15 [Major] spec S1 AC and plan 1.2 (`tests/dsh/test-live-digest.sh`): "match -> PASS" is unreachable with only a chosen `x-measure-guard-digest` header, because `live_check` also requires `x-measure-guard-module` to equal `$PLUGIN_TARGET/index.js` (otherwise WARN) and a session id via `--session`/`DSH_SESSION_ID` (otherwise SKIP). Rationale: the named normal case as specified observes WARN or SKIP, so the fixture's headers and the expected outcome are incomplete.
- F16 [Major] spec Decision 8 and plan 3.1: the shell targets are extracted as "absolute or relative" but the plan never states that a relative target resolves against the session-effective directory, the base that file mutations use through `resolveMutationPath`/`normalizeMutation` in `src/hooks.js`; `editDecision`/`tddDecision` need an absolute path (`isInside`), and `prepareDecision` passes `dir` only to the file branch. Rationale: `echo x > out.txt` then reaches the decision as a non-absolute path and fails open, so the most common shell write form escapes the new check, and the existing resolution helper is not named.
- F17 [Major] spec Decision 5 and plan 2.1: `git cat-file -e <sha>` exits 0 for any existing object, so a tree, blob, or tag SHA passes the "is this a commit" probe and the planned "no commit in this repository owns" problem never fires for it, while the note probe then reports it as "its commit". Rationale: S2's purpose is to prove the SHA is a real commit, and the described probe cannot distinguish object types (verified: a blob SHA returns 0).
- F18 [Major] spec Decision 5/S2 AC and plan 2.1/2.2: the `shaProblems` design runs `cat-file -e` and `notes show` for every `[x]` task with no short-circuit, but `git notes show` on an absent SHA also exits 1, which the seam maps to `missing`, so one bad SHA yields two problems (commit and note) while S2 and 2.2 require exactly one. Rationale: the implementer must choose between the AC and the bullet, and the resulting problem count is user-visible.
- F19 [Nit] spec NFR-4: NFR-4 calls Decision 7 "the one intentional fail-closed change", but Decision 8's registry deny for shell writes is also an intentional fail-closed rule over content the guard cannot read. Rationale: the wording understates the fail-closed surface without changing what is built.
- F20 [Major] spec Overview item 3: it still says "a `git add` inside the same commit command is invisible to the commit guard's no-task rule", but the current guard sets `takesChanges` for any preceding `git add` (`parseCommitCommand` in `src/core/guards.ts`) and unions every changed and untracked status path, and Decision 9 now describes exactly that over-approximation. Rationale: the root-problem statement contradicts Decision 9 and the code, so the reader gets the opposite diagnosis of the gap the track closes.
