## Round 1

Date: 2026-11-07

### What this track proposes

This track makes the guard mode effective per repository: the persisted `repos.json` override and an in-memory session override compose above the profile config, are read per call through one `deps.modeOf(root)` seam by the guards, the note/reminder, the turn-end hold, and the client view, and are exposed in the state route, the band, `measure_status`, and `/measure-status`. It adds `/measure-mode` to report, set, and clear the session and repository overrides, and the read-only `/measure-verify` to report the active plan's git-backed problems plus the active track's `metadata actual_tasks` verdict, failing open instead of throwing. Docs, a live strict-deny probe with its run record, and the track closeout complete it, all adapter-side with no shared-core change, no new dependency, and both parity gates green.

### How the current system works, per this spec

The adapter resolves `config.mode` once at `apply` (`parseModeOf`) and hands that static value to every guard, the `measure_status` tool, and the state route, while `Repos.modeOf`/`setMode` in `src/state.js` are exercised only by tests and no command changes the mode. The git-backed task problems run only at `agent/turn-stopping` and the closeout `metadata.json` check only inside a `tracks.md` close edit, so both are turn-end or edit-triggered. The current host commands are `measure-off`, `measure-on`, `measure-status`, and `measure-goal` plus the eight workflow commands, and the state route and band carry no mode.

### Findings

- F1 [Blocker] plan.md Task 1.1: The plan never names the file that holds the new in-memory session store (`Modes`) and `effectiveMode`: the first bullet sits under `src/state.js` while the third names `src/modes.js` (new) only for `measureModeCommand`. Rationale: the zero-decision check forbids leaving a file location to the implementer.
- F2 [Blocker] plan.md Task 2.1: The metadata verdict has no rule for an open track: a new track's `metadata.json` carries `actual_tasks: null` (the current track's file does), so "when its plan's `[x]` count disagrees with `metadata.json`" fires on a clean in-progress track and reports the closeout text "closed with metadata actual_tasks null", making S2's "verification clean" reply unreachable until closeout; NFR-4 also says a missing metadata file degrades to `nothing to verify`, and the plan does not say how the active track supplies the `ClosingTrack {entry, plan}` that `closeoutMetadataCheck` (`src/git-verification.js`) requires. Rationale: edge-case behavior and the check's input shape are left to the implementer, and two required replies cannot both hold.
- F3 [Blocker] plan.md Task 2.1: A git that cannot answer cannot produce `nothing to verify (<reason>)` through the named seam: `shaProblems` (`src/git-verification.js`) skips a probe that returns `error` and returns `[]` when `deps.gitProbe` is missing, so a real git failure yields the clean reply; only a throwing seam reaches the catch. Rationale: the required fail-open reply is unreachable with the named reuse, and the detection point is left open.
- F4 [Blocker] plan.md Task 1.1: `src/client-state.js` and `src/client.js`: the plan says the view gains `mode: { value, source }` but not what `clientView` now accepts (the `{value, source}` result, or the legacy config string with an invented `source: 'config'`) or how `registerClientState(ctx, { mode })` receives the async seam, since `clientView` is synchronous and the register call currently carries the static string. Rationale: API shape left to the implementer; the existing tests call `clientView({ mode: 'guard' })`.
- F5 [Major] plan.md Task 1.1: The seam consumer list names `guardContext`, `prepareDecision`, `onTurnStopping`, `context.js`, and `status.js` but omits `src/strict.js` `recordRed` and `guard.js` `commitGuardFor`, which also gate on `deps.mode === 'strict'` (`tddGuardFor` has the same read and is only incidentally covered by the edit-guard test); it also never says whether `deps.mode` is removed or kept as the config value. Rationale: a strict override would leave the commit guard and the Red record on the config mode, and whether those paths must change is decided by the implementer.
- F6 [Major] spec.md S1 Acceptance Criteria: "Given `/measure-mode strict`, When the next tool call is prepared, Then it uses `strict` and the source is `session`" conflicts with "Given both a repository and a session override, Then the repository override wins"; the strict AC states no precondition excluding a repository override. Rationale: a test written from the spec alone can contradict one of the two ACs; only plan Task 1.2 resolves the order.
- F7 [Major] plan.md Task 2.1: `verifyReport(deps, agent)` is specified as `-> { text }`, while the exact replies are strings and the command handlers return `{ kind: 'success', text }`; the plan never says whether the command wraps a string or the report returns an object. Rationale: API shape left to the implementer.
- F8 [Major] plan.md Task 2.1: Comprehension gap: `<n>` in `verification clean (<n> tasks checked).` is undefined: all top-level tasks, `[x]` tasks, or `[x]` tasks with a SHA. Rationale: an exact-text contract with an undefined count cannot be tested unambiguously.
- F9 [Major] plan.md Task 2.1: The plan does not say whether `verifyReport` refreshes the snapshot; `deps.snapshots.get(root)` returns the cached snapshot (`src/snapshot.js` `Snapshots.get`), while `measure-status` calls `refreshSnapshotOf` (`src/status.js`) first. Rationale: "right now" is the command's purpose, and a cached snapshot can report a commit or note state the operator has already fixed.
- F10 [Major] plan.md Task 1.1: Comprehension gap: `<scope>` in the set/clear texts is undefined (`repo` or `repository`, `session` or `this session`), and the set text has no effective-mode clause, so `/measure-mode strict` under a repository override replies "mode set to strict (session)" while the effective mode stays the repository's; `/measure-mode default` with no override also has no defined reply. Rationale: the exact-text contract and the shadowed-set case are left to the implementer.
- F11 [Major] plan.md Task 1.2: No named test covers the end-of-turn hold or the context note as mode consumers, so two of the four consumers in spec Decision 3 are untested; the listed tests cover `effectiveMode`, the command, the view, and the edit guard only. Rationale: a phase's test cases must cover the consumers it changes.
- F12 [Major] plan.md Task 2.2: The `/measure-verify` tests omit the read-only property that spec S2's last AC requires (no file, plan, repository, or metadata change). Rationale: an acceptance criterion without a named test.
- F13 [Major] plan.md Task 1.1: The new in-memory mode store duplicates `Bypass` (`src/state.js`), which already keeps a root-keyed session set with `get`/`set`/`clear` and repository-first precedence. Rationale: zoom-out check 4, new code where cited existing code does the job.
- F14 [Major] spec.md Decision 4 and S1 Acceptance Criteria: Decision 4 says the band renders "the value (localized)", while S1's band AC says both show "the effective mode and its source"; plan Task 1.1 repeats the value-only wording and names no test for the client label (`tests/client-bundle.test.js` is not extended). Rationale: contradictory documents and an untested acceptance criterion.
- F15 [Nit] spec.md Overview: "The git-backed task problems and the closeout `metadata.json` check run at `agent/turn-stopping` and inside a tracks edit" reads as if the metadata check also runs at turn-stopping; only `shaProblems` runs in `onTurnStopping`, and `closeoutMetadataCheck` runs in `closeoutGuardFor` on a `tracks.md` edit (`src/guard.js`). Rationale: a false description of the current system.
- F16 [Nit] plan.md preamble and spec.md Decision 7: "both parity gates" never names the two commands (`plugins/dsh-measure-guard/scripts/check-parity.sh` and `plugins/opencode-measure-guard/scripts/check-parity.sh`). Rationale: concreteness of the gate.
